# IOMTea 系统核心价值分析与微信小程序集成可行性

> 2026-05-23

---

## 1. 当前系统核心价值

| 维度 | 能力 | 差异化 |
|------|------|--------|
| **边缘 AI** | 设备端 IMU 跌倒检测 + 活动/姿态分类 | 不需要云端推理，离线可用，隐私安全 |
| **数据中继** | Android 作为 BLE Hub，汇总健康设备数据 → MQTT/HTTP 双通道上传 | 一台手机代理多个 BLE 外设，降低每设备 SIM 成本 |
| **离线韧性** | SQLite 缓存 + 重试队列 | 无网络时正常工作，联网后自动补传 |
| **实时告警** | 跌倒 300ms 内本地通知 + MQTT QoS1 紧急上报 | 比云端方案延迟低一个数量级 |
| **轻量部署** | EMQX + PostgreSQL，Docker Compose 一键启动 | 家庭自部署，无云服务费 |
| **身份体系** | PIN 码设备绑定，支持多设备 | 一人多设备，一户多用户 |

**核心定位**：家庭健康边缘网关 —— Android 手机作为传感器数据入口、BLE 中继、实时告警引擎，后端仅做存储和查询。

---

## 2. 不完善点

| 类别 | 缺口 | 影响 |
|------|------|------|
| **数据可视化** | 无历史曲线、无健康趋势分析 | 用户不知道数据"意味着什么" |
| **家庭协作** | 无法绑定多个监护人、无法共享设备 | 跌倒告警只能通知 APP 持有者 |
| **健康报告** | 无周报/月报、无异常总结推送 | 缺乏"产品感"，数据沉睡 |
| **第三方集成** | 无微信/支付宝生态入口 | 中国家庭用户触达受阻 |
| **BLE 外设** | 规范已写，代码未实现 | 血压/血氧/体温数据无法接入 |
| **GPS 轨迹** | 未接入 | 老人走失/出门未归无法感知 |
| **用药提醒** | 无 | 健康管理闭环缺失 |
| **YOLO 视觉** | GPU 兼容性崩坏 | 姿态识别仅依赖 IMU |

## 3. 微信小程序集成 — 可行性分析

### 3.1 Flutter 不能直接变小程序

Flutter 编译为 ARM 原生码，微信小程序运行在 JavaScriptCore/V8 引擎中。二者运行环境完全不同，**无法直接将 Flutter 代码转译为小程序**。

### 3.2 正确架构：Flutter + 小程序分工

```
┌── Flutter Android ──────────┐    ┌── WeChat Mini Program ──────┐
│ 传感器采集 (IMU/BLE/GPS)     │    │ 健康数据查看 (图表/报告)       │
│ 本地推理 (跌倒/活动分类)      │    │ 告警接收 (模板消息)            │
│ BLE 中继 → MQTT 上传         │    │ 家庭共享 (多监护人绑定)        │
│ 离线缓存 + 重试              │    │ 用药提醒设置                  │
│ 后台长驻守护                 │    │ 微信一键登录 (免 PIN)          │
└──────────┬──────────────────┘    └──────────┬───────────────────┘
           │                                  │
           └────────────┬─────────────────────┘
                        │
              Backend API (统一)
              ├── MQTT broker
              ├── tRPC HTTP
              └── PostgreSQL
```

| 职责 | Flutter | 小程序 |
|------|---------|--------|
| 传感器访问 | ✅ | ❌ 无 API |
| BLE 扫描/连接 | ✅ | ❌ 仅支持蓝牙广播读取 |
| 后台持续运行 | ✅ | ❌ 前台 5 分钟后挂起 |
| 本地通知/振动 | ✅ | ❌ 仅模板消息 |
| 数据可视化 | ⚠️ 能做 | ✅ 更适合（转发/分享） |
| 社交分享 | ❌ | ✅ 微信生态天然 |
| 模板消息推送 | ❌ | ✅ 高触达率 |
| 微信支付 | ❌ | ✅ |
| 一键登录 | ❌ | ✅ wx.login() |
| 轻量访问 | ❌ (需安装) | ✅ (扫码即用) |

### 3.3 可行性结论：**高度可行，且互补**

Flutter 做采集端（传感器/网络/后台），小程序做展示端（查看/分享/提醒）。无需解决"Flutter 转小程序"这个伪命题。

## 4. 数据格式一致性

### 4.1 统一 Event Schema

两端的健康事件使用完全相同的 JSON 结构：

```json
{
  "deviceId": "abc123",
  "pin": "123456",
  "event": "activity_change",
  "subtype": "walking",
  "confidence": 0.85,
  "timestamp": 1716460800000,
  "accel_mag": 10.5,
  "source": "iomtea-android"
}
```

后端 `health_events` 表的字段与 Flutter 的 `HealthEvent` 模型一一映射：

| Flutter HealthEvent | PostgreSQL health_events | 小程序接收 |
|---------------------|--------------------------|-----------|
| timestamp | time | ✅ |
| type | event_type | ✅ |
| subtype | subtype | ✅ |
| confidence | confidence | ✅ |
| accelMag | accel_mag | ✅ |
| metadata | metadata (JSONB) | ✅ |

### 4.2 认证一致性

| 端 | 认证方式 | 备注 |
|----|---------|------|
| Flutter | 6 位 PIN 码 | 设备绑定，本地持久化 |
| 小程序 | wx.login() → openId | 绑定 openId → PIN，后台关联 |
| 后端 | JWT token | 两种登录方式签发同一格式 token |

### 4.3 通信协议一致性

| 场景 | Flutter | 小程序 |
|------|---------|--------|
| 实时数据上报 | MQTT | 不需要（小程序不上报） |
| 历史数据查询 | HTTP tRPC | HTTP REST（同一后端） |
| 实时告警 | MQTT + 本地通知 | 微信模板消息（后端触发） |
| 设备在线状态 | MQTT retained | HTTP /api/v1/device/online |

## 5. 小程序功能规划

```
首页 Tab:
├── 实时概览 — 设备在线状态、今日步数、跌倒次数
├── 健康数据 — 心率/血压/体温历史曲线
├── 告警中心 — 跌倒/异常事件时间线
└── 我的 — 设备管理、绑定的老人、用药提醒
```

- **模板消息**：跌倒告警 → 微信服务通知（比 Android 通知触达率高得多）
- **家庭共享**：监护人可以扫码绑定被监护人的设备
- **周报推送**：每周一推送"本周健康概况"
